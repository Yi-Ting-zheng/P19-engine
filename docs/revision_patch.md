## R1：异构纯度——从「基座异构」到「观测维度正交」

### 1.1 问题诊断

v1.0 的「原生异构基座」约束不够——DeepSeek-V3、Claude-3.5、MiMo 虽然参数不同，但：
- 训练数据高度重叠（都读过同样的数学文献）
- RLHF 对齐方向相似（都被训练成「礼貌、不承认不知道」）
- Transformer 架构相同（同一归纳偏置）

**类比**：三个同一法医学院毕业的法医看同一具尸体——他们的「独立」意见可能系统性偏向同一个错误。

### 1.2 v1.1 修订：观测维度正交定义

> **异构 ≠ 基座不同；异构 = 观测维度正交。**

**操作性定义**：两个房间的观测维度正交，当且仅当它们的**判定依据类型**在认识论上不可互推。

### 1.3 四基座观测维度分配方案

| 房间 | 基座 | 观测维度 | 判定依据 | 真值产出类型 |
|------|------|---------|---------|-------------|
| **Room-F** | DeepSeek-V3 | **形式化** | Lean 类型检查、公理依赖图、trdeg 推导链 | 编译通过性、公理集、缺口分类 |
| **Room-N** | MiMo-V2.6 | **数值** | mpmath PSLQ、高精度探针、参数扫描 | EMPIRICAL 支持/反例、效应量 |
| **Room-S** | Claude-3.5 | **语义** | 证明结构合理性、定义一致性、隐含假设识别 | 语义漏洞、定义漂移、隐式公理 |
| **Room-A** | OpenCode | **对抗** | 反例搜索、边界条件、最小反例构造 | 反例、边界失效、退化情形 |

### 1.4 正交性验证矩阵

**判定依据不可互推检查**：

| | Room-F（形式化） | Room-N（数值） | Room-S（语义） | Room-A（对抗） |
|---|---|---|---|---|
| **Room-F** | — | ✗ 不可互推 | ✗ 不可互推 | ✗ 不可互推 |
| **Room-N** | ✗ | — | ✗ | ✗ |
| **Room-S** | ✗ | ✗ | — | ✗ |
| **Room-A** | ✗ | ✗ | ✗ | — |

**不可互推的含义**：
- 形式化验证通过 ≠ 数值验证通过（Schanuel 硬墙就是例子：形式化编译通过，但数值无法证实）
- 数值验证通过 ≠ 语义合理（35 档仿真全吻合，但命题可能是恒真式零信息）
- 语义合理 ≠ 对抗存活（证明看起来对，但边界条件可能有反例）

### 1.5 表决资格修正

```
v1.0：参与表决房间基座必须原生异构
v1.1：参与表决房间观测维度必须正交，且每个维度至少 1 个房间
```

**最低配置**：4 房间（形式化/数值/语义/对抗各 1）
**推荐配置**：6 房间（每个维度 2 个房间，同维度内用不同基座冗余）

## R2：投票门槛——分层投票 + 关键判定清单

### 2.1 问题诊断

v1.0 的「达成一致」未定义粒度——全等太严（一个房间卡死全部），多数太松（掩盖系统性错误）。

### 2.2 v1.1 修订：两层投票机制

| 层级 | 判定类型 | 投票规则 | 违反后果 |
|------|---------|---------|---------|
| **L0 关键判定** | GAP-OPEN 分类、THEOREM-COND 升格、硬墙识别 | **全等**（所有房间一致） | 冻结相变，送人工裁决 |
| **L1 非关键判定** | 缺口描述措辞、建议优先级、修复路径 | **多数**（≥⌈N/2⌉+1） | 记录分歧，不阻断相变 |

### 2.3 关键判定清单（L0）

> 依据：`assumption_inference.md` §5 真值层级状态机 + §6 刚性十条 + §10 证算分离纪律

| # | 关键判定项 | 依据条款 | 全等要求 |
|---|-----------|---------|---------|
| K1 | 缺口分类：工程疏漏 vs 数学硬墙 | §1.2 两个关键区分 | ✅ |
| K2 | 真值层级：EMPIRICAL / THEOREM-COND / THEOREM | §5 状态机 | ✅ |
| K3 | 硬墙识别：GAP-OPEN 是否正确标记 | §6 规则 7（证伪不删除） | ✅ |
| K4 | 升格合法性：是否满足 THEOREM-COND 条件 | §6 规则 5（定理升格唯一通路） | ✅ |
| K5 | 递归升级禁令：是否有多次 EMPIRICAL 试图升格 THEOREM | §6 规则 6（不可跳跃） | ✅ |
| K6 | 证算分离：每步是否标注【证】/【算】/【恒】 | §10.1 规则 1 | ✅ |
| K7 | 等价≠归约：是否有重述冒充进展 | §10.1 规则 6 | ✅ |

### 2.4 非关键判定清单（L1）

| # | 非关键判定项 | 多数要求 |
|---|-------------|---------|
| N1 | 缺口描述的措辞优化 | ≥⌈N/2⌉+1 |
| N2 | 修复路径的优先级建议 | ≥⌈N/2⌉+1 |
| N3 | 补充文档的引用建议 | ≥⌈N/2⌉+1 |
| N4 | 台账备注的补充信息 | ≥⌈N/2⌉+1 |

### 2.5 投票流程

```
房间报告 → 发现层解析 → 审计层校验
    ↓
关键判定（L0）→ 全等检查
    ├── 一致 → 进入非关键判定
    └── 分歧 → 冻结，送人工裁决
    ↓
非关键判定（L1）→ 多数检查
    ├── 达到多数 → 受控相变
    └── 未达多数 → 记录分歧，继续（不阻断）
```

## R3：P19 时序协议——三步分离

### 3.1 问题诊断

v1.0 把「76s 并行」和「相变能力」混在一起。P19 严格含义是**跨域势能差打开相变窗口**，不是**并行加速**。

### 3.2 v1.1 修订：P19 时序协议

> **三步严格分离，不混淆：**

| 步骤 | 名称 | 功能 | 时间属性 | P19 对应 |
|------|------|------|---------|---------|
| **Step-1** | 并行生成 | N 房间同时观测标本，各自输出报告 | 工程优化，可压缩 | 不对应 P19 |
| **Step-2** | 冲突检测 | 比对 N 份报告，识别分歧点 | 检测，可自动化 | P19 前置条件 |
| **Step-3** | 相变仲裁 | 对冲突点执行分层投票，决定升格/冻结 | 质变，不可压缩 | **P19 相变窗口** |

### 3.3 时序图

```
时间轴 ──────────────────────────────────────────────────────►

Step-1 并行生成（工程优化）
├── Room-F ──────────┤
├── Room-N ──────────┤
├── Room-S ──────────┤
├── Room-A ──────────┤
                     ↓
Step-2 冲突检测（自动化比对）
                     ├── 无冲突 ──→ 直接升格（THEOREM-COND/THEOREM）
                     └── 有冲突 ──→ 进入 Step-3
                                    ↓
Step-3 相变仲裁（P19 相变窗口）
                                    ├── 关键判定全等 ──→ 受控相变
                                    └── 关键判定分歧 ──→ 冻结 + 人工裁决
```

### 3.4 性能目标修正

| 指标 | v1.0 | v1.1 |
|------|------|------|
| Step-1 并行生成 | 76min → 数十秒 | 76min → **76s**（工程优化目标） |
| Step-2 冲突检测 | 未定义 | **<5s**（自动化比对） |
| Step-3 相变仲裁 | 未定义 | **不可压缩**（P19 相变窗口，取决于冲突复杂度） |
| **总计** | 「数十秒」 | **76s + 5s + T_arbitration** |

**关键认知**：Step-3 的时间**不应该被压缩**——相变发生在冲突被识别并仲裁的那一刻，压缩它等于压缩 P19 本身。

### 3.5 P19 严格对齐

> P19 相变外驱定理：纯稳态封闭系统无法通过内源运算完成自我重构。相变窗口仅由**跨域外部势能差**唯一打开。

**v1.1 对齐**：
- Step-1（并行生成）= 内源运算，不产生相变
- Step-2（冲突检测）= 识别势能差的存在
- Step-3（相变仲裁）= **跨域势能差实际打开相变窗口**

**冲突本身就是 P19 说的「跨域势能差」**——Room-F 说「这是公理」、Room-A 说「这可证」的那一刻，就是稳态裂隙。

## R4：人脑角色——从「真值裁判」到「意义锚点 + 伦理签字」

### 4.1 问题诊断

v1.0 把人脑放在「真值裁判」位置，但：
- 人脑有上下文连续性问题（批量裁决可能忘记历史判定）
- 人脑不是形式化验证的对手（顶级科学家也做不到跟上 AI 速度）
- 真值稳定性不应该依赖人的记忆

### 4.2 v1.1 修订：人脑角色降格 + 台账升格

| 维度 | v1.0 | v1.1 |
|------|------|------|
| **真值裁判** | ✅ 人脑负责 | ❌ 版本化台账负责 |
| **意义锚点** | 未定义 | ✅ 人脑负责 |
| **伦理签字** | 未定义 | ✅ 人脑负责 |

### 4.3 人脑新职责定义

#### 职责 1：意义锚点

人脑回答的问题不是「这个命题是真的吗」，而是：

> **「这个命题对我们有意义吗？值得继续投入资源吗？」**

| 判定类型 | 判定问题 | 输出 |
|---------|---------|------|
| 方向性 | 这条证明路径值得继续吗？ | GO / NO-GO |
| 优先级 | 这个缺口应该优先修复吗？ | P0 / P1 / P2 |
| 资源分配 | 应该投入更多算力吗？ | 增加 / 维持 / 减少 |

#### 职责 2：伦理签字

人脑回答的问题不是「这个证明是对的吗」，而是：

> **「这个结果可以发布/使用吗？符合伦理规范吗？」**

| 判定类型 | 判定问题 | 输出 |
|---------|---------|------|
| 发布合规 | 这个结果可以公开吗？ | APPROVE / REJECT |
| 使用边界 | 这个结果的使用场景有伦理风险吗？ | 无风险 / 有限制 / 有风险 |
| 责任归属 | 如果结果出错，谁负责？ | 签字确认 |

#### 职责 3：硬墙分类确认（保留）

人脑回答的问题：

> **「此处红点是可补疏漏还是不可补深渊？」**

| 判定类型 | 判定问题 | 输出 |
|---------|---------|------|
| 硬墙分类 | 这是工程疏漏还是数学硬墙？ | FIXABLE / ABYSS |
| 复活条件 | 如果是硬墙，什么条件下可以重审？ | 条件描述 |

### 4.4 真值稳定性保障

**核心原则**：真值判定不依赖人脑的实时记忆，依赖**版本化台账**。

```yaml
truth_ledger:
  version: "v2026.10.11.001"
  specimen_hash: "abc123..."
  judgments:
    - judgment_id: "J-001"
      type: "GAP_CLASSIFICATION"
      item: "GAP-001 (SchanuelAt)"
      verdict: "ABYSS"
      human_signer: "human_001"
      timestamp: "2026-10-11T10:00:00Z"
      evidence: "P0研究报告 + M6-04缺口分析"
      reversible: true
      reconsider_when: "Schanuel猜想被证明"
      
    - judgment_id: "J-002"
      type: "RELEASE_APPROVAL"
      item: "Specimen-002"
      verdict: "APPROVE"
      human_signer: "human_001"
      timestamp: "2026-10-11T11:00:00Z"
      conditions: "必须附带硬墙标注"
      
  previous_version: "v2026.10.10.002"
  append_only: true
```

**关键特性**：
- 每次人脑裁决都是**增量**，不覆盖历史
- 真值判定可追溯、可审计、可回滚
- 人脑不需要记住历史判定，系统自动检测冲突

### 4.5 人脑接地协议修正

```
v1.0：批量裁决（每小时），人脑判定真值
v1.1：增量裁决（按需），人脑签字意义 + 伦理，真值由台账维护
```

## 修订依据：本次自指拷问

### 拷问 1：异构够不够异构？

**v1.0 回答**：基座不同就够
**v1.1 修正**：基座不同 ≠ 观测维度正交。DeepSeek/Claude/MiMo 都是 Transformer，共享训练数据，可能系统性偏向同一个错误。

**修正逻辑**：C-02 说「独立性由规则+观测维度之差承载，与基座无关」——v1.0 只做了基座隔离，没做观测维度隔离。

### 拷问 2：一致性在哪里？

**v1.0 回答**：「达成一致」（未定义粒度）
**v1.1 修正**：分层投票——关键判定全等，非关键判定多数。

**修正逻辑**：全等太严（一个房间卡死全部），多数太松（掩盖系统性错误）。关键判定（如硬墙识别）必须全等，非关键判定（如措辞优化）允许多数。

### 拷问 3：76s 是相变还是并行？

**v1.0 回答**：76s 并行相变（混在一起）
**v1.1 修正**：Step-1 并行生成（76s）+ Step-2 冲突检测（5s）+ Step-3 相变仲裁（不可压缩）。

**修正逻辑**：P19 说相变需要「跨域势能差」，不是「并行加速」。冲突本身就是势能差，压缩冲突检测等于压缩 P19 本身。
